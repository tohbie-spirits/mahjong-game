## 1. Project Analysis

### What we're building
A single-player, offline-capable, browser-based Mahjong game supporting three independent rulesets (Riichi, Hong Kong, Chinese Official), each with 3- or 4-player configurations against AI opponents of two difficulty tiers. Premium desktop-app-quality UI, full persistence via LocalStorage, no backend dependency for gameplay.

### Key architectural challenges
1. **Ruleset isolation** — Riichi, Hong Kong, and Chinese Official scoring/yaku/fan systems are structurally different (e.g., Riichi's han/fu vs. Hong Kong's fan-only vs. Chinese Official's point-based rule combination system). These must NOT share logic beyond truly universal primitives (tile identity, basic set validity). Each gets its own self-contained rule module behind a common interface.
2. **AI modularity** — AI must plug into any ruleset via a shared interface (`evaluateHand()`, `chooseDiscard()`, `chooseAction()`), with ruleset-specific strategy injected rather than hardcoded.
3. **Deterministic core / decorative shell separation** — Game logic (turn resolution, wall state, scoring) must be fully decoupled from rendering and animation, so the engine is testable headlessly and the UI is swappable.
4. **Incremental buildability** — Because this is built one small task at a time across many sessions, every module must be independently completable and testable without waiting on unfinished siblings. This drives the task ordering below (core primitives → single ruleset vertical slice → UI shell → AI → remaining rulesets → polish).
5. **Persistence architecture** — Settings, stats, leaderboards, and in-progress game state all need namespaced LocalStorage schemas designed up front so later features don't require migrations.

### Recommendations (for your approval)
- **Build one ruleset "vertically" first** (Hong Kong Mahjong — simplest scoring model) all the way from wall → deal → turns → win detection → scoring → basic AI → minimal UI, before starting Riichi or Chinese Official. This gives a fully playable game early, which then becomes the template for the other two rulesets. I've ordered the tasks this way below.
- **Use a lightweight internal event bus** (pub/sub) between Core Engine and UI layer instead of direct calls, so animations/audio can hook into game events without polluting game logic.
- **Canvas vs DOM for tiles**: I recommend DOM + CSS (absolutely positioned tile elements) rather than `<canvas>`. This gives us free accessibility (focus, ARIA), easier hit-testing for drag/click, and CSS transitions for animations, at negligible performance cost for a turn-based game like Mahjong.
- **Defer audio/music assets** to a later phase — we'll build the AudioManager module and interfaces early (so calls exist in code) but wire in actual sound files near the end, since asset sourcing/licensing is a separate concern from engineering.
- **Version the LocalStorage schema** from day one (`{ schemaVersion: 1, ... }`) so future changes don't corrupt existing users' saved stats/leaderboards.
- **Accessibility**: keyboard navigation for tile selection/discard, ARIA live regions for turn announcements, and a color-blind-safe tile theme option — I'll fold these into the relevant UI tasks rather than a single bolted-on task.

Let me know if you'd like to change the "Hong Kong first" ordering or any of the above before we start Task 1.

**Layer responsibilities**

| Layer | Responsibility |
|---|---|
| Core Engine (Tile, Wall, Player, Turn Managers) | Ruleset-agnostic game state and flow |
| Rule Engine (3 modules) | Everything ruleset-specific: legal actions, win validation, yaku/fan detection, scoring, terminology |
| AI Manager | Strategy layer; consumes Rule Engine's legal-action queries; Basic/Advanced tiers per ruleset |
| Game Manager | Orchestrator wiring Core Engine + Rule Engine + AI Manager together for a session |
| UI Layer | Menus, dialogs, tile renderer, animation engine — subscribes to Game Manager events, never touches rule logic directly |
| Persistence Layer | LocalStorage-backed Settings/Stats/Leaderboard/Save managers, versioned schema |
| Audio Manager | Sound effects/music playback, independent of game logic |

### Core interfaces (conceptual, not code yet)
- `RuleEngine`: `getLegalActions(state, player)`, `checkWin(hand, context)`, `scoreHand(hand, context)`, `getTerminology()`
- `AIStrategy`: `chooseDiscard(state, player, ruleEngine)`, `chooseAction(state, player, legalActions, ruleEngine)`
- `StorageManager`: `get(key)`, `set(key, value)`, `namespace(domain)` — all schema-versioned

## Known Issues

**NOTE — Tasks 108–110: all sound is synthesised, and was judged by measurement, not by ear.** Effects and music are generated with the Web Audio API (no files — offline and licence-free, as the plan's deferred-assets recommendation allows). They were checked for structure in Node (recording fake context) and for level in Chrome (OfflineAudioContext renders: every effect audible, none clipping, music ≈ −28 dBFS RMS under the effects), but the build environment has no speakers — a listening pass on real devices is still worth doing, and recorded sounds can replace any recipe later without other changes.

**MINOR — Task 112: on the smallest phones (≈ 360 × 640) the table can grow ~20 px taller than the screen late in a 4-player hand.** (Task 118 fixed a related flaw found by sampling whole hands: a side seat's name tag was wider than its 3.2rem column on phones and could spill off-screen and onto its discard pile late in a hand.) By design the centre row grows (the page scrolls a little) rather than letting discard piles overlap seats. Discard tiles on portrait phones are 17 px wide — legible but small; Task 115's accessibility pass may want a "large tiles" option.

**RESOLVED (mitigated) at Task 80b — found at Task 80: the Advanced defence layer (Task 77) did not pay on the real engine.** Task 80's cross-run comparison called it net-neutral; Task 80b's exactly-paired same-table measurement showed it was HARMFUL (−5.7 points per seat-hand [−9.2, −2.2] vs no defence on the tuning walls, −6.3 pp wins, no deal-in reduction). Two causes, both diagnosed on real games: (1) MIS-CALIBRATION — the danger score ranks tiles well (AUC 0.75 vs Basic, 0.82 vs Advanced opponents) but averages ≈0.40 while real Hong Kong deal-in rates are ≈0.3% (vs Basic) / ≈0.8% (vs Advanced) per discard, so BALANCE gave up speed for safety ~50× too eagerly; (2) VALUE-BLIND THREAT — under the 3-fan minimum, opponents with no exposed melds Ron only ≈0.02% of discards and opponents whose exposed melds cap them below 3 fan never did (0 of ~4,000), yet the threat clock treated them like everyone else. FIX: progressWeight 1 → 10 and tenpaiProgressWeight 3 → 30 (thresholds unchanged — folding earlier still costs wins), plus a value-aware threat scale (no exposed melds × 0.1; melds below the minimum × 0.05). RESULT on untouched walls 40000–40299, all-Advanced table (the only Advanced table the real game creates — Task 79 gives every AI seat one tier): tuned defence vs NO defence −0.5 points [−2.2, +1.2], deal-ins −2.5 pp; the old Task 77 defence on the same walls −1.3 [−3.5, +0.9] (and −2.6 [−4.6, −0.5] on walls 30000+). REMAINING (not fixed, recorded honestly): no defence setting tried beats NO defence on points on held-out walls — at best it is neutral at an all-Advanced table while cutting deal-ins, and against Basic opponents it still costs ≈1.8 points [−3.5, −0.1] per seat-hand (a table the game never builds). Defence stays ON by default for that reason; `new AdvancedStrategy({ useDefense: false })` is the one-line alternative if pure points ever matter more than playing safe.

**RESOLVED at Task 118 — found by the regression QA pass: the human could never call Chi / Pon / Kong on another player's discard.** A limitation noted at Task 41 ("no decision mechanism for a human seat yet") that had silently survived into the finished game: the engine passed every such call for the human. GameManager can now stop a discard for the human's call (`setHumanClaimPrompts`, `awaiting-claim`, `resolveHumanClaim`); the game screen asks, with a Hint. The human's Ron on a discard stays automatic (see the note below).

**NOTE — Task 118: a winning discard is always taken for the human (Ron is automatic).** Declining a Ron is rarely right, and in Riichi it would need the temporary-furiten rules for the human seat; the rules reference and tutorial say so. A candidate for later polish.

**RESOLVED at Task 119 — found at Task 80: occasional slow Advanced decisions.** The shanten search is now computed suit by suit and memoized (identical results — checked against the old search on 150,000 hands): Advanced turns p99 156 → 12 ms, worst 366 → 27 ms in Node; long tasks in a browser session ~100 → 3. Original note:
**MINOR — found at Task 80: occasional slow Advanced decisions.** Uncontended Node timings: median ≈ 1.5 ms, p95 ≈ 20–27 ms, but single decisions up to ≈ 0.25–0.4 s (value scoring of many tenpai waits). In the browser this is a brief stall inside the AI turn delay, not a correctness problem. Candidates for Phase 10 polish: cache scoreHand results per hand state, or run AI turns in a Web Worker.

**RESOLVED at Task 78b — found at Task 78: the Advanced AI was fan-blind under Hong Kong's 3-fan minimum.** Tasks 73–77 optimise speed to ANY complete shape (shanten/ukeire) plus defence; they never consider whether the finished hand will SCORE. With the minimum at 3 fan, Advanced reaches tenpai with hands too cheap to win and cannot declare. Measured on 120 identical seeded hands (2 Advanced vs 2 Basic, seats swapped): minimum 0 fan → Advanced 99 wins / Basic 22, +159 points; minimum 1 → 88 / 27, +170; minimum 3 (the real setting) → 12 / 26, −440, with Advanced ending 162 hands tenpai-but-unable-to-win. So the efficiency/claim/defence logic is strong; the missing piece is value planning. Recommended fix (inserted as Task 78b, before Task 79 makes Advanced selectable): route-aware evaluation — for each candidate discard compute constrained shanten for the routes that reach the minimum (mixed/pure one suit, all pungs, honour pungs, concealed + self-drawn) and their expected fan, prefer the fastest route that can meet the minimum, treat "tenpai on waits that can't reach the minimum" as not tenpai (checked with the real RuleEngine#scoreHand), and let claim evaluation credit fan (e.g. Pon toward all-pungs / honour pungs, Chi only inside a flush plan). FIX (Task 78b): new `HandValuePlanner.js` scores four routes per hand (plain, valuable honour pung, one-suit flush, all pungs) with the fan each guarantees and takes the fastest route that reaches the minimum as the hand's VALUE shanten; at tenpai every wait is scored with the real RuleEngine#scoreHand, so a tenpai that can't be declared no longer counts as tenpai. Discards, claims (a Chi that throws away Concealed with no route left is passed; dragon/seat/prevailing-wind Pons are credited) and self-Kongs all rank by value shanten. RESULTS at the real 3-fan minimum: tuning seeds 7900 (120 hands) Advanced 41 wins / Basic 24, +96 points; HELD-OUT seeds 12000 (300 hands, never used for tuning) Advanced 106 / Basic 46, deal-ins 29 vs 72, +1088 points, 0 fallbacks — versus the fan-blind path on the same seeds: 39 / 60, −656. All-Advanced tables: 23 wins in 40 hands (was 8). 1-fan results unchanged (88 / 26, +296).

Kept here as a record, not because anything is currently outstanding.)*

**Found at Task 39, fixed at Task 42 — `WinResolver.js`'s `resolveRonWin()` scored an incomplete hand.** It called `ruleEngine.scoreHand(player.getHand(), ...)` without ever adding the claimed discard tile — the real hand was genuinely short exactly one tile at that point, silently under-counting any composition-dependent fan pattern (All Sequences, All Triplets, flush checks). This stayed invisible until Task 42's harness ran real games at volume and started recording actual Ron wins with `meetsMinimum: false` despite `chooseWinDeclaration` having correctly approved them using accurate (complete-hand) scoring — the decision and the execution were scoring two different hands. Fixed by extracting the "build a temporary complete hand view without mutating real state" technique (previously duplicated three times — once correctly in `DrawResolver.js`, correctly again in `BasicStrategy.js`, and this one incorrectly) into one canonical `createHandViewWithExtraTile()` export on `Hand.js`, now used by all three call sites.

**Found and fixed at Task 42 — a claimed Kong never drew its required replacement tile.** `TurnInterruptionResolver.js`'s `applyClaimResolution()` sent every claim type (Chi, Pon, *and* Kong) straight to `AWAITING_DISCARD`, but a Kong — claimed from a discard or self-declared, doesn't matter which — always needs a replacement draw before the claiming seat can discard. Self-declared Kongs already got this right (`GameManager.declareKong()` handles it), but a *claimed* Kong silently skipped it, meaning a player who claimed several Kongs over a hand would eventually run out of concealed tiles to discard from entirely, crashing `BasicStrategy.chooseDiscard()`. Reproduced directly (`[BasicStrategy] Seat N has no tiles to discard from`) after ~100-1000 real simulated hands. Fixed by having `applyClaimResolution()` leave a claimed Kong at `AWAITING_DRAW` instead, with `GameManager.performDiscard()` following up with its own `performDraw()` call — reusing the exact same wall-exhaustion-aware draw path `declareKong()` already relied on, rather than duplicating that logic a second time.
